# Fix the commit-and-push freeze by uncovering the progress that already exists, not by making git faster

## Context and Problem Statement

The maintainer reports: *"the commit message window pops up, the commit message
gets populated, then I hit commit and push, and it takes 30+ seconds with the
app frozen before it completes the push. Even with 1 file."*

"Even with 1 file" is the load-bearing clue: this is **fixed overhead**, not
work proportional to the change. A previous record,
[0020-MADR-fetch-pull-push-lag.md](0020-MADR-fetch-pull-push-lag.md)
(`accepted`, plan `executed`), already addressed lag in fetch/pull/push — the
pull split, `--progress` streaming, the busy gate, and refresh scope. That
record audited **fetch, pull and push**. It never audited the **commit**
surface, which is where this complaint starts.

The question this record answers is not "how do we make git faster". It is:

> Where do the 30 seconds actually go, which of them are ours, and why does the
> app appear **frozen** rather than merely busy?

Those are three separate questions with three different answers, and conflating
them is how this gets "fixed" without the user noticing any difference.

## Audit method

Four parallel read-only agents: an end-to-end command trace of Accept+Push; the
post-mutation refresh fan-out; a regression check of every 0020 fix; and a pass
dedicated to UI blocking as distinct from slowness. Measurements were taken on
this Mac (macOS 26.6.2, git 2.55.0, Apple silicon, warm cache) in **throwaway
repos under `/private/tmp`** and by read-only reproduction of hook logic against
this repo. No network remote was pushed to; the working tree was not modified.

**One theory was tested and refuted rather than shipped** — see "What the
measurement refuted".

## The 30 seconds, measured

| Component | Cost | Ours? |
|---|---|---|
| **`pre-push` hook (801 blobs, ~1602 process spawns)** | **~8.7–9.5 s** | **No** — user's `~/.global-git-hooks/pre-push` |
| Network push to github.com over HTTPS + `gh auth git-credential` | unmeasured (local bare-repo push = 0.10 s, so effectively all remaining B5 time) | No |
| `git commit` including hook | **0.03–0.13 s** | Ours, and cheap |
| Pre-push probes (upstream remote, remote URL) | ~0.05 s warm; +2 commands cold | Ours |
| `_logPushed` bookkeeping (2 reads, one a real `diff --name-status`) | ~0.1–0.3 s | Ours, and **inside the frozen window** |
| Post-mutation refresh fan-out (**4 full-set invalidations**, ≈22–40 git processes) | seconds locally, worse over SSH | Ours |

Three agents measured the `pre-push` figure independently (9.48 s / 8.80 s /
8.65 s) on this repo, at one outgoing commit.

**So roughly a third of the wall-clock is one shell loop in a hook outside this
codebase, and essentially none of it is `git commit`.** The rest of the app's
contribution is real but measured in seconds, not tens of seconds.

### And yet the app is not compute-blocked at all

Frames render at 60 fps throughout. Nothing on this path does seconds of
main-isolate work. The app is **input-blocked and feedback-free**, which is
indistinguishable from a hang:

* the composer is a `showMacosSheet` modal whose barrier covers the **entire**
  commit + push + refresh span, because `Navigator.pop` runs only at the end
  (`repo_status_view.dart:779`, `commit_dialog.dart:102`);
* `barrierDismissible` defaults to false, so nothing behind it is clickable;
* Escape is deliberately swallowed while committing
  (`commit_dialog.dart:61-64`);
* both buttons are disabled — `canAccept` is false while `committing`
  (`commit_composer_controller.dart:101`, `commit_composer.dart:275-289`);
* **no spinner exists for `committing`.** The only `ProgressCircle` in the sheet
  is gated on `loadingPreview` (`commit_composer.dart:238-239`);
* the status line keeps reading *"Generated by prepare-commit-msg. Review,
  Edit, or Accept."* for the whole 30 s (`commit_composer.dart:472-489`).

The cruellest detail: **`git push --progress` is already streaming live output
the entire time**, through `_streamGitOp` → `OutputLogNotifier.startStream`
(`repo_status_view.dart:179-202`), and the Activity Center is already ticking.
0020 built that. The modal sheet is sitting on top of it. The only visible
feedback is the macOS **Dock** progress bar — off-window, easily missed.

So the headline defect is not slowness. It is a modal that hides the very
progress indicator this codebase already built, tells the user to click a button
it has disabled, and refuses Escape.

## What the measurement refuted

Two agents independently inferred a compelling story: the app commits with `-m`
and no `--no-verify`, git therefore runs `prepare-commit-msg` a second time, that
hook is a 6.8 MB Go binary that calls an LLM, and it holds `ExecLane.exclusive`
— starving every read in the app — for 10–30 s. It fits the symptom exactly.

**It is false.** Measured directly:

* `git commit -m "…"` under the real `core.hooksPath`: **0.039 s** (parent
  session), **0.03 s** (agent, independently).
* Control, proving the mechanism was tested rather than assumed: the same
  command with a deliberate `sleep 5` hook takes **5.37 s**.
* The binary exports `main.shouldSkipSource` and
  `…/internal/git.IsCommitMsgEmpty` — it self-suppresses when a message is
  supplied.

The LLM cost (**3.72 s**, measured) is paid **once**, when the sheet opens — the
"message gets populated" step, before the click, on `ExecLane.isolated` where
0022 M2 put it.

This matters beyond bookkeeping. Acting on the inference would have meant adding
`--no-verify` to every commit — silently disabling every user hook in the app,
to fix a cost that does not exist. It is recorded here so nobody re-derives it.

The exclusive-lane starvation is therefore **latent, not acute**: real
(`command_lanes.dart:249-275`, and the scheduler is an app-lifetime singleton
per backend, so one commit starves reads in *every* repo, tab and pop-out), but
currently ~0.1 s. A future hook that does not self-suppress would make it acute.

## Findings — bugs in fetch / pull / push / sync

0020's fixes were re-verified and **all hold** (pull split, `--progress` on every
network op, on-queue stderr streaming, fetch/push not holding `_busy`, cached
auth probes, no automatic `ls-remote`, `activityIdle` on the network command,
the dedicated SSH sync client). 0022's cache invalidation costs two **local**
commands (~50 ms) once per branch switch and reintroduces nothing.

What is broken:

**B1 — `_push` invalidates all 11 mutation families. 0020 H5 shipped for fetch
and never for push.** `repo_status_view.dart:983-1001` passes no `refresh:`, so
`busy_action.dart:152` falls back to the full set — re-walking `git log` (200
commits), `logSearch` (500-commit page), `stash list`, `reflog --max-count=200`,
snapshots and `worktree list` after an operation that moved neither HEAD, the
index, nor the worktree. `repoFetchFamilies`' own docstring
(`app_providers.dart:2937-2946`) says it is the right set for "a fetch **or
push**". Compare `_fetch`, which passes it correctly (`:866`).

**B2 — commit, push, pull and sync are not wrapped in `withOwnMutation`, so the
app refreshes in response to its own writes.** `withOwnMutation`
(`app_providers.dart:2751`) is applied to fetch (`repo_status_view.dart:852`)
and `_fetchPrune` only. Consequences: `git commit` writes `.git/COMMIT_EDITMSG`
~250 ms in — which **survives the watch filter**
(`watch_path_filter.dart:13-40` drops `*.lock`, `/objects/`, `/logs/`,
`/fsmonitor--daemon/`, not this) — firing a full 11-family invalidation
*mid-commit*, which then queues behind the commit's own exclusive barrier. A
push writes `refs/remotes/**` and does it again. This is 0020 H6, unfixed on
exactly the paths that matter here.

**B3 — the commit sheet invalidates a fourth time, orphaning in-flight reads.**
`commit_dialog.dart:92` calls `refreshAfterMutation` after `submit()` returns —
after `_push` already refreshed (B1). Riverpod discards the in-flight results,
but the orphaned `git` processes run to completion still holding read-lane
slots. The hazard is documented in this very codebase at
`repo_status_view.dart:518-526`.

**Net: a one-file Commit+Push fires four full-set fan-outs — ≈22–40 git
processes.** With `repoFetchFamilies` semantics and own-mutation suppression it
is one snapshot plus two reads.

**B4 — pull's integrate half can be killed mid-rebase.** `git_service.dart:5086-5094`
runs merge/rebase through `_run` with no `timeout:`, taking
`SSHCommandExecutor.defaultTimeout` (60 s). A rebase of many commits, or a merge
invoking a merge driver or `post-merge` hook, is SIGTERM'd at 60 s leaving
`.git/rebase-merge` behind. This matches 0020's frozen spec — the plan asserted
these halves "are local", which does not bound them — so it is a latent
correctness bug, not a regression.

**B5 — `pushTags`, `deleteRemoteTag`, `deleteRemoteBranch`, `lsRemoteTags` take
no `onOutput`** (`git_service.dart:5223, 5257, 4183, 5295`). 0020's Phase 5a
listed them; only fetch/pull/push landed. A tag push through the 9 s `pre-push`
hook shows a blank, apparently-hung output view.

**B6 — the failure path double-logs.** `busy_action.dart:142` emits a second
`$ <title>` header plus the whole buffered output after `_streamGitOp` already
streamed it and closed the session; for `_sync` the two headers disagree
(`git sync` vs `git pull --ff-only`).

**B7 — `_publishBranch` pushes under `runGuarded` with no streaming**
(`branches_view.dart:1163-1172`; same in `create_pr_form.dart:204`,
`create_mr_form.dart:209`) — the pre-0020 shape, inconsistent with `_push`.

**B8 — `parseRefsDetailed` is never isolate-gated.** `git_service.dart:2156-2159`:
the porcelain parse one line above is gated at 32 KiB, and the `for-each-ref
refs/heads refs/remotes refs/tags` parse directly below — routinely the *larger*
section — is not. This is the only mechanism found that can freeze **frames**
rather than merely spin panes, and it runs on every snapshot, i.e. four times per
commit+push today.

**B9 — in Review mode, a forge API call sits on the post-commit path.**
`branchBaseProvider` is in `repoMutationFamilies` and, with
`allowForgeFetch: true` (`branches_view.dart:298`), awaits `repoMergePolicyProvider`
→ a `gh`/`glab` call (a bare `gh` spawn alone measures 59 ms; a real round trip
is far more).

## Decision Drivers

* The user's complaint is "frozen", and the fix for "frozen" is not the fix for
  "slow". Optimising git while leaving the modal in place would change the
  number and not the experience.
* The largest single term is **outside this codebase**. An honest record has to
  say so plainly rather than quietly optimising around it.
* This app already built streaming progress, an Activity Center, and Dock
  progress. Surfacing what exists beats adding machinery.
* 0020 decided the refresh-scope direction; two of its items were only half
  landed. Finishing a decided thing outranks inventing a new one.
* Fixed overhead per operation is what makes a tool feel slow — a 30 ms probe on
  every push is felt more than a proportional cost on a large change.

## Considered Options

* **A. Optimise the git commands.** Fewer probes, batched bookkeeping, tighter
  refresh. Real, but leaves the freeze — a third of the wall clock is a hook we
  do not control, and the modal hides the progress either way.
* **B. Make the app honest about long operations, then finish 0020's refresh
  work, then trim fixed overhead** — in that order, and report the hook fix to
  the maintainer as the single largest win.
* **C. Suppress user hooks (`--no-verify`) on the app's commit/push.** Would
  "fix" the number by disabling the user's own tooling, including a secret
  scanner. Rejected: it silently removes a safety net the user installed
  deliberately, and the measurement shows the commit hook costs nothing anyway.

## Decision Outcome

Chosen option: **B**, because the reported defect is a *feedback* defect wearing
a performance costume. The app is responsive, streaming progress, and tracking
the operation in two places — behind an opaque modal that disables its own
buttons and swallows Escape. Fixing that changes the user's experience of all
30 seconds without removing one of them; the performance work then removes the
seconds that are genuinely ours.

Option C is rejected on principle as well as on evidence: the app must not
disable a user's hooks to flatter its own timings.

**This record does not authorise implementation.** A paired plan is required, per
the repository's workflow.

### The three performance improvements

**P1 — Stop covering the progress that already exists.** Render a real
`committing` / `pushing` state in the composer (spinner plus "Pushing to
origin/master…" in `_statusText`, `commit_composer.dart:238, 472`), and **pop
the sheet the moment the commit lands**, letting the push finish behind the
workspace where its live output, Activity Center entry and Dock progress are
already visible. `submit()` already distinguishes `localCommitted` from
`pushSucceeded` (`commit_composer_controller.dart:331-366`), so the seam exists.
Also narrow the Escape interception to the commit half.
*Win: removes the entire perceived freeze — 0 ms of git saved.*

**P2 — Finish 0020 H5 and H6 for commit and push.** `_push` passes
`refresh: () => refreshAfterFetch(...)`; wrap commit/push/pull/sync in
`withOwnMutation`; ~~drop the redundant invalidation at
`commit_dialog.dart:92`~~ **→ see Amendment A1 below: it is not redundant, and
dropping it would ship a refresh gap. Give the sheet's commit a refresh
contract instead**; filter `COMMIT_EDITMSG` in `watch_path_filter.dart`; move
`_logPushed`'s two reads off the awaited path (0020 M3, which landed against
`_busy` but not against this surface's modal).
*Win: four full-set fan-outs → one; ≈22–40 git processes → ≈6; removes the
mid-commit refresh that queues behind the commit's own barrier.*

**P3 — Delete the fixed per-push overhead.** Resolve the upstream remote from
`GitBranchInfo.upstream`, already in RAM from the snapshot, instead of the
`sh -c` probe (measured **37.6 ms** vs 12.4 ms for a plain `git config`, and one
SSH round trip remotely) — this is 0020 M1's stated direction, of which only the
caching half shipped, and it makes 0022's cache invalidation free because there
is nothing left to re-probe. **→ Amendment A2 below: this is not the
substitution it reads as. That field holds `origin/main`, not a remote name, and
`GitService` holds no cached snapshot to read it from.** Gate the forge
credential helpers on the remote's
scheme, since git ignores them for SSH remotes and `fetch --all` currently
installs **both** helpers, walking `gh` (**102 ms** measured) before `glab`.
Also give pull's integrate half a real timeout (B4) and `onOutput` to the four
network ops that lack it (B5).
*Win: −40 ms and −1 SSH round trip per cold push; −100 ms per HTTPS remote on
multi-remote fetch; removes a corrupted-rebase failure mode.*

### The two algorithmic improvements

**A1 — Batch `_sync`'s bookkeeping from six processes into one.** `_sync`
(`repo_status_view.dart:1020-1079`) issues four `rev-parse` and two
`diff --name-status` around its three network commands — including a **literally
duplicated `rev-parse HEAD`** (`:1062` and `:1077`). This is precisely the
pattern `_runCaptured` already solves (`git_service.dart:5935-5945`): one
`sh -c` with `$(…)` captures and a `printf` separator stream.
*O(n) spawns → O(1): six processes → one, −65 ms locally, −5 SSH round trips.*

**A2 — Make History incremental instead of re-walking it.** Every mutation
refresh re-runs `git log` for 200 commits and `logSearch` for a 500-commit page
(`git_service.dart:2390`), then re-parses and re-renders both. A commit appends
one commit; a fetch/push only ever appends on the remote-tracking side. Fetching
`rev-list <old>..<new>` and prepending turns the cost from *page-sized* to
*delta-sized*.
*O(page) → O(new commits): the common case becomes one commit instead of 200,
and it compounds with P2 by making the refresh that does remain cheap.*

**Companion (external, and the largest algorithmic win available):** the
`pre-push` hook is `O(files-in-repo)` where it should be `O(files-in-the-diff)`.
`~/.global-git-hooks/pre-push:65-79` enumerates each outgoing commit's **entire
tree** via `git rev-list --objects <c> -1` and then spawns **one `git cat-file
blob` plus one `grep` per blob** — 801 blobs, ~1602 processes here. Two
equivalent one-pass forms, measured against the identical predicate:

| Form | Measured |
|---|---|
| current per-blob loop | **8.80 s** |
| `git cat-file --batch \| grep -aE` | **0.059 s** |
| `git grep -aE '<pattern>' <commit>` | 0.078 s |

**~149× for the same check, 1602 processes → 2.** Scoping it to
`git diff-tree -r <remote_sha>..<local_sha>` as well would make it proportional
to the push. This file is the maintainer's and outside this repository; it is
recorded here because it is the single largest term in the reported 30 seconds,
and no change inside Magic Git will move it.

#### Executed 2026-09-03, at the maintainer's instruction ("go fix the pre hook
#### first") — and it turned out to be a security fix, not only a speed fix

**A silent false negative was found and fixed.** The hook tested for matches
with `grep -q` at the end of a pipeline under `set -o pipefail`. `grep -q` exits
the instant it matches, which SIGPIPEs the upstream `git cat-file`; pipefail
then reports the signal (**141**) and the `if` reads a genuine match as *clean*.
The bug gets more likely the larger the file, which is precisely backwards for a
secret scanner.

Demonstrated before the change, through a real `git push`: a 20 MB blob with
`a denied token` **on line 1** pushed successfully past the guard (exit 0). Isolated to
confirm the mechanism rather than guess it — the pipeline returned 141 while
`grep -c` over the same blob reported 1 match. Both the **content** scan and the
**author/committer identity** scan used that construct, so both were affected.

Fix: a `grep_has()` helper that counts instead of short-circuiting, so it
consumes all input and its exit status reflects the match and nothing else. Same
boolean contract, no false negative.

**Performance, same predicate and same object set:** one `cat-file --batch` pass
over the deduped blob list replaces the per-blob `cat-file blob | grep` pair.
Per-blob reads now happen **only** when the fast pass has already found
something, purely to name the offending OIDs for the message — so a clean push
never pays them.

Verified against the real repository, 17 outgoing commits, 870 blobs, no push
performed (refs fed to the hook on stdin exactly as git does):

| | Original | Fixed |
|---|---|---|
| Real-repo scan, 17 outgoing commits | **10.208 s** | **0.559 s** |
| Clean `git push` of 803 blobs (throwaway repo, local remote) | **10.132 s** | **0.588 s** |

**~18× end-to-end on a real push.**

Behaviour re-verified after the change — each guard was observed **firing**, not
merely assumed intact: content leak in a blob (blocked, and reporting the
*identical* offending OID as the original), internal author/committer identity
(blocked), annotated-tag message (blocked), the previously-missed 20 MB blob
(**now blocked**), and a clean push (still allowed). The original is backed up
at `pre-push.ORIGINAL.bak` in this session's scratchpad.

### Consequences

* Good, because the user's actual complaint — "frozen" — is answered directly,
  and by uncovering existing machinery rather than building new machinery.
* Good, because P2 finishes work that was already decided in 0020 rather than
  opening a new direction, and closes the mid-commit self-refresh.
* Good, because the largest term is named honestly as external and quantified,
  so effort is not spent optimising the app to hide someone else's shell loop.
* Neutral, because P1 changes an interaction model: the sheet dismissing while a
  push continues in the background is a deliberate behaviour change and needs a
  decision, not just an implementation.
* Bad, because A2 (incremental history) is the largest change here and touches
  paging, search and the commit-graph — it is a candidate, not a small fix, and
  a plan must decide whether it is worth its regression risk.
* Bad, because none of this is verified against a live `.app`. Every number
  above is from a shell or from source; the freeze itself was diagnosed by
  reading UI state, not by watching the app.

## Amendments (2026-09-03, before any implementation)

Writing the paired plan meant gathering the exact current code for every edit
site. That pass found **two of this record's own prescriptions to be wrong as
written**. Both are corrected here rather than in the plan alone, because a
reader who follows only the MADR would otherwise implement a defect.

The original wording is struck through above rather than rewritten, so the
record shows what was decided and what disproved it.

### Amendment A1 — P2's "drop the redundant invalidation" would ship a refresh gap

`commit_dialog.dart:92`'s `refreshAfterMutation` is **not redundant**. The two
commit surfaces do not share a path:

* **Dock** (`repo_status_view.dart:824-826`) commits inside `runGuarded`, whose
  `finally` calls `refreshAfterAction()` → the full `repoMutationFamilies` set.
  Line 92 never runs on this path.
* **Sheet** (`commit_dialog.dart:81-86`) calls `git.commit` **raw** — no
  `runGuarded`, no `runLogged`, no refresh of any kind. Line 92 is the **only**
  invalidation the sheet's commit ever gets.

With `push: false` it is already the sole refresh. With `push: true` it is
covered today *only* because `_push` does a full-set refresh — **which P2 itself
removes**. So deleting line 92 after narrowing `_push` would break both sheet
variants, and would do so only *after* the optimisation landed, which is the
worst possible ordering for noticing it.

**Corrected direction:** give the sheet's commit the same refresh contract the
dock already has (one full-set refresh for the *commit*), and let `_push` do the
narrow fetch-set refresh for the *push*. `submit()` offers no callback between
its commit and push phases, so this needs a small seam there — which P1 already
introduces for its own reasons.

### Amendment A2 — P3's upstream substitution is not a rename

Two independent problems, both of which would produce a silent auth failure —
the exact class of bug 0022 M1 was written to prevent:

1. **`GitBranchInfo.upstream` is the upstream *shorthand* (`origin/main`), not
   the remote name.** Deriving the remote requires a **longest-prefix match
   against the snapshot's `remotes` list**, never `split('/').first`: remote
   names may legally contain `/`, and a branch tracking a *local* branch yields
   a bare branch name with no remote prefix at all. The existing probe
   special-cases that as `'.'` (`git_service.dart:4981-4983`); porcelain never
   prints `.`, so a naive split would return e.g. `main` as a "remote name" and
   silently install no credential helper.
2. **`GitService` holds no cached snapshot.** `_snapshotInFlight`
   (`git_service.dart:1947`) holds in-flight futures only, cleared on
   completion. Calling `_snapshot()` from `push()` would issue a whole new
   combined round trip — **worse than the 37.6 ms probe it was meant to
   replace**, which inverts the entire point.

**Corrected direction:** plumb the value in from the caller — `repo_status_view`
already holds it in RAM via `statusProvider` — as an optional parameter, keeping
the existing probe as the fallback when it is absent.

Two cases the snapshot cannot answer and the probe can, both degrading to
`origin` (auth-only degradation, the same class the probe's own fallback
accepts): an unborn branch with a configured upstream — whether git emits
`# branch.upstream` alongside `# branch.oid (initial)` is version-dependent and
was **not** verified against a live git — and a half-configured
`branch.<n>.remote` with no resolvable `.merge`. The plan requires verifying the
unborn case against real git during execution rather than assuming it.

### What these two have in common

Both read as mechanical substitutions and are not. Both would have removed a
safety property while appearing to be pure optimisation, and neither would have
failed loudly: A1 shows up as stale History after a commit, A2 as an HTTPS auth
failure on some branches but not others. They are recorded at this length
because "obvious cleanup" is exactly the shape of change that gets executed
without re-derivation.

## Confirmation

Confirmed by: an end-to-end command trace with lanes and timeouts for every
command on the Accept+Push path; three independent measurements of the
`pre-push` cost (9.48 / 8.80 / 8.65 s at 801 blobs); a direct measurement of
`git commit -m` under the real hooks path (**0.039 s**) with a `sleep 5` control
proving the hook mechanism was exercised (**5.37 s**); measurement of the LLM
preview (3.72 s) and of per-command process overhead on this Mac (`Process.start`
floor 7.7 ms; a typical git read 12–15 ms; `gh auth git-credential` 102 ms);
and a full regression check of 0020's shipped fixes against current source.

**Not** confirmed by: a running `.app`, a live push to github.com (deliberately
not performed), or an SSH session. The network component of the push is
unmeasured. Before a plan is executed, the freeze should be observed once in the
real app with the Dock progress bar visible, to confirm the UI diagnosis the way
the hook cost was confirmed.
